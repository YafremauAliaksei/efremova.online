# 🔐 07 — База данных: можно ли её взломать и как этому помешать

> Прямой ответ на вопрос владельца: **да, взломать можно почти любую систему.**
> Вопрос не в том, «можно или нельзя», а в том, сколько это стоит атакующему
> и что он получит, если всё-таки пробьётся.
>
> Наша цель — сделать так, чтобы: (1) добраться было дорого, (2) добравшись,
> он получил нечитаемый мусор, (3) мы узнали об этом в тот же час.

---

## 1. Почему PostgreSQL, а не что-то ещё

| Вариант | Вердикт | Почему |
|---|---|---|
| **PostgreSQL** ✅ | **берём** | Транзакции, шифрование полей, Row Level Security, 30 лет репутации. Используется в банках и медицине |
| MySQL / MariaDB | можно | Тоже надёжна, но слабее с JSON, строгими типами и политиками доступа на уровне строк |
| MongoDB | ❌ | Нет транзакций «из коробки» в нашем сценарии. Исторически тысячи баз утекли просто потому, что по умолчанию слушали интернет без пароля |
| SQLite | ❌ | Отличная для одного пользователя. Не выдержит параллельных записей и не умеет ролевого доступа |
| Готовые облачные (Supabase, Firebase) | ⚠️ | Удобно, но мед. данные окажутся у третьей стороны, а часть — за пределами ЕС. Для GDPR это отдельный договор и отдельный риск |

Ключевой аргумент за PostgreSQL в нашем случае — **Row Level Security**:
база сама, независимо от кода, отказывается показывать клиенту А строки клиента Б.
Даже если программист однажды напишет запрос без фильтра — утечки не произойдёт.
Это защита от человеческой ошибки, а не только от злоумышленника.

## 2. Как вообще ломают базы данных — и чем мы закрылись

Разберём реальные способы, в порядке частоты в реальном мире.

### 2.1 База торчит в интернет (причина №1 всех утечек)

**Как происходит:** порт `5432` открыт наружу. Поисковики вроде Shodan
находят такие базы за минуты и ведут их публичные списки.

**Как закрыто у нас:** в [`docker-compose.yml`](../docker-compose.yml) у контейнера
базы указано `expose`, а не `ports`. Разница фундаментальная:

```yaml
ports:  ['5432:5432']   # ❌ порт виден из интернета
expose: ['5432']        # ✅ порт виден только другим контейнерам
```

Подключиться к базе снаружи невозможно физически — не «запрещено правилом»,
а именно невозможно: наружу проброшен только nginx (80 и 443).

Когда понадобится посмотреть базу с ноутбука — делается SSH-туннель:

```bash
ssh -L 5432:localhost:5432 user@server
```

Порт при этом остаётся закрытым для всех, кроме владельца SSH-ключа.

### 2.2 SQL-инъекция

**Как происходит:** в поле «имя» вводят `'; DROP TABLE users; --`, и если запрос
собирается склейкой строк — команда выполняется.

**Как закрыто:** Prisma не склеивает строки, а передаёт значения отдельно от запроса
(параметризация). Текст `'; DROP TABLE` останется просто текстом — базе он придёт
как значение, а не как команда. Плюс линтер запрещает сырой SQL, плюс Semgrep
в CI ищет такие места, плюс RLS в базе как последний рубеж.

Это тот случай, когда защита не «мы старались», а «эта атака технически невозможна
в нашей архитектуре».

### 2.3 Слабый или утёкший пароль базы

**Как закрыто:**
- пароль генерируется случайно (`openssl rand -base64 32`), в коде его нет;
- аутентификация `scram-sha-256` — самый стойкий метод PostgreSQL;
- пароль в `.env`, который не в git и не в публичном репозитории;
- даже зная пароль, снаружи подключиться некуда (см. 2.1).

### 2.4 Кража резервной копии

Часто забываемый вектор: сама база защищена, а дамп лежит в облаке открытым текстом.

**Как закрыто:** в [`infra/docker/backup.sh`](../infra/docker/backup.sh) дамп
шифруется **до** попадания на диск — pg_dump → gzip → age → выгрузка, одним потоком.
Незашифрованная копия не существует нигде, даже временно.

### 2.5 Взлом самого сервера

Самый серьёзный сценарий: получили доступ к серверу — значит, получили и доступ к базе.

**Что это даёт атакующему на самом деле:**

```
Что он увидит в таблице session_notes:

  id          | 8f2a...
  content     | \x9f3e7a2b8c1d4f5e6a7b8c9d0e1f2a3b4c5d6e7f...
  iv          | \x4a5b6c7d8e9f0a1b
  key_version | v1

Это всё. Ключ расшифровки в базе НЕ хранится.
```

Ключ живёт в отдельном хранилище секретов. Чтобы прочитать заметки, атакующему
нужно скомпрометировать **две независимые системы**, а не одну. Это и называется
многоуровневой защитой: одна дыра не равна катастрофе.

### 2.6 Человеческий фактор

Самая частая причина в реальности: скачали прод-базу «посмотреть», забыли на ноутбуке,
ноутбук украли. Поэтому в правилах проекта есть жёсткий запрет
(docs/03, красные линии): **прод-база на личном компьютере — никогда.**
Для разработки используются демо-данные из `prisma/seed.ts`.

## 3. Разработка на локальном ПК через Docker

То, что просил владелец: всё крутится локально, ничего не настраивается вручную.

```
     ВАШ КОМПЬЮТЕР
┌────────────────────────────────────────────────┐
│  🐳 Docker Desktop                             │
│                                                │
│  ┌──────────────┐      ┌──────────────┐       │
│  │ PostgreSQL   │      │    Redis     │       │
│  │ демо-данные  │      │ сессии, OTP  │       │
│  └──────┬───────┘      └──────┬───────┘       │
│         │ порт 5432 открыт    │ 6379          │
│         │ ТОЛЬКО на localhost │               │
└─────────┼─────────────────────┼───────────────┘
          │                     │
    ┌─────▼─────────────────────▼─────┐
    │  npm run dev (Next.js)          │
    │  http://localhost:3000          │
    └─────────────────────────────────┘
```

Команды — три штуки:

```bash
docker compose up -d postgres redis
```

```bash
npm run db:migrate
```

```bash
npm run db:seed && npm run dev
```

> **Почему локально порты 5432 и 6379 всё-таки открыты, а на сервере — нет.**
> Локально они привязаны к `127.0.0.1` — это адрес «только этот компьютер»,
> из сети к нему не подключиться. На сервере же порт был бы виден всему интернету,
> поэтому там используется `expose`. Разница в одной строке конфигурации,
> и она — между «удобно разрабатывать» и «база в публичном списке Shodan».

### Переезд на VPS в будущем

Ничего переделывать не придётся — в этом и смысл Docker.
Отличий ровно три, и все они в конфигурации, а не в коде:

| | Локально | На VPS |
|---|---|---|
| Порт базы | `127.0.0.1:5432` | закрыт, только `expose` |
| Пароли | простые тестовые | случайные 32 байта |
| Данные | демо из `seed.ts` | настоящие, шифрованные |

## 4. Что шифруется, а что нет — и почему

Шифровать всё подряд — ошибка: по зашифрованному полю нельзя искать и сортировать.
Поэтому решение принимается по каждому полю отдельно.

| Данные | Шифруем | Почему |
|---|---|---|
| Заметки о сессиях | 🔐 **да** | Врачебная тайна. Самое чувствительное в системе |
| Анкета первичного приёма | 🔐 да | Содержит описание состояния |
| Имя, email, телефон | 🔐 да | Сам список клиентов психолога — уже чувствительная информация |
| Ссылка на видеозвонок | 🔐 да | Ссылка = доступ к сеансу |
| Даты и время сессий | ❌ нет | Нужны для поиска слотов и сортировки. Раскрывают факт визита, но не содержание |
| Суммы платежей | ❌ нет | Нужны для отчётности и сверки |
| Статусы, роли, флаги | ❌ нет | Не несут личной информации |
| Журнал аудита | ❌ нет | По нему нужно искать. Медицинского содержимого там нет по правилу |

Отдельно: пароли не хранятся вообще — их в системе нет (passwordless-вход).
То, чего нет, украсть невозможно.

## 5. Честная оценка: какие риски остаются

Никакая система не даёт 100 %. Что остаётся и что с этим делать:

| Риск | Вероятность | Что делаем |
|---|---|---|
| Дыра «нулевого дня» в PostgreSQL или Next.js | низкая | Автообновления, Dependabot, еженедельный скан |
| Кража устройства владельца с активной сессией | **средняя** | Короткие сессии (15 мин), 2FA обязательна, «выйти со всех устройств» |
| Фишинг владельца | **средняя** | Аппаратный ключ или passkey для аккаунта психолога — это лучшая защита |
| Подрядчик (Hetzner, Cloudflare) допустил утечку | низкая | DPA-договоры, шифрование на нашей стороне — им видны только шифротексты |
| Ошибка в коде, открывшая чужие данные | средняя | RLS в базе, обязательный code review, тесты на права доступа |
| Юридическое требование выдать данные | — | Отвечает владелец, не система. Порядок описывается в политике конфиденциальности |

**Самое слабое звено в этом списке — не база данных, а человек.**
Именно поэтому 2FA для аккаунта психолога в проекте не опция, а требование:
один этот аккаунт открывает доступ ко всем клиентам сразу.
