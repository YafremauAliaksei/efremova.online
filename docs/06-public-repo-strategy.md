# 🔓 06 — Публичный репозиторий: как открыть код, не открыв личное

> Задача владельца: код должен быть **реально проверяемым** — любой человек может
> посмотреть, как устроена защита данных. При этом в репозитории не должно быть
> ни одного личного или секретного байта.
>
> Это нормальная инженерная практика, а не компромисс. Правило Керкгоффса
> (1883 год, криптография): **стойкость системы должна зависеть только от ключа,
> а не от секретности устройства замка.** Если система ломается от того,
> что кто-то увидел её код, — она была сломана с самого начала.

---

## 1. Главный принцип: разделение «как» и «что»

```
┌──────────────────────────────────┬──────────────────────────────────┐
│   ПУБЛИЧНЫЙ РЕПОЗИТОРИЙ          │   ЗАКРЫТЫЙ СЕРВЕР                │
│   (виден всем на GitHub)         │   (виден только владельцу)       │
├──────────────────────────────────┼──────────────────────────────────┤
│   КАК устроен сайт               │   ЧТО на сайте написано          │
│                                  │                                  │
│ • код страниц и логики           │ • тексты «Обо мне», «Подход»     │
│ • схема базы данных              │ • фотографии                     │
│ • правила безопасности           │ • реальные цены                  │
│ • конфиги nginx, Docker          │ • отзывы                         │
│ • .env.example (ИМЕНА ключей)    │ • .env (ЗНАЧЕНИЯ ключей)         │
│ • демо-данные-заглушки           │ • данные клиентов                │
│ • история изменений              │ • заметки о сессиях              │
└──────────────────────────────────┴──────────────────────────────────┘
```

Технически это достигается одним решением: **весь контент сайта лежит в базе данных,
а не в коде.** Поэтому в репозитории физически нечему утечь — там только пустые формы.

Как это реализовано:

| Что | Где живёт | Что в репозитории |
|---|---|---|
| Тексты страниц | таблица `content_blocks` | модель + демо-заглушки в `prisma/seed.ts` |
| Услуги и цены | `services` + `service_prices` | структура + круглые демо-цены |
| Отзывы | `testimonials` | два отзыва с подписью «Демо-отзыв» |
| Лекции | `lectures` (кэш YouTube) | только структура |
| Ключи и пароли | `.env` на сервере | `.env.example` с именами и пояснениями |
| Данные клиентов | зашифрованные поля в базе | ничего |

Побочный плюс, который важнее, чем кажется: тексты правятся через админку,
**без программиста и без выкладки новой версии сайта**.

## 2. Что НИКОГДА не попадает в репозиторий

Список короткий, потому что каждый пункт — инцидент.

```
❌ .env с настоящими значениями
❌ Любые ключи: *.pem, *.key, service-account.json, id_rsa
❌ terraform.tfstate (внутри — IP, токены, структура инфраструктуры)
❌ Дампы базы: *.sql, *.dump, backups/
❌ Реальные фото и тексты владельца
❌ Скриншоты с настоящими данными клиентов (даже размытые)
❌ IP-адрес сервера в коде (он в переменных Terraform)
❌ Настоящие email и телефоны — даже в комментариях и тестах
```

Всё перечисленное уже перекрыто в [`.gitignore`](../.gitignore). Но `.gitignore` —
это только первая линия: он защищает от невнимательности, а не от опечатки в пути.
Поэтому есть вторая и третья линии (п. 4).

## 3. Почему открытый код не делает сайт уязвимее

Частое возражение: «взломщик увидит, как всё устроено». Разберём честно.

| Что увидит посторонний | Даёт ли это доступ | Почему |
|---|---|---|
| Схему базы данных | ❌ нет | Знание, что есть таблица `session_notes`, не даёт к ней подключиться |
| Список путей-ловушек | ⚠️ частично | Умный взломщик их обойдёт. Но 99 % атак — автоматические сканеры, которые читают не GitHub, а список типовых путей. Ловушки ловят именно их |
| Правила WAF | ⚠️ частично | Настоящие управляемые правила Cloudflare в репозитории не лежат — они на их стороне |
| Алгоритм шифрования | ❌ нет | AES-256 открыт и опубликован. Без ключа расшифровать нельзя, и это математика, а не секретность |
| Логику проверки прав | ✅ **плюс** | Ошибку в ней скорее найдёт доброжелательный читатель, чем взломщик |
| Версии библиотек | ⚠️ да | Это реальный риск: видно, есть ли у нас необновлённая библиотека с известной дырой. **Закрывается Dependabot + еженедельным сканом в CI** |

Единственный настоящий минус — последняя строка, и он полностью снимается
автоматическим обновлением зависимостей. За это мы получаем то, что нельзя купить:
**сайт психолога, про который можно честно сказать клиентам «код открыт, проверьте сами,
как я храню ваши данные».** Для медицинской тематики это сильный аргумент доверия.

Так делают Signal, Bitwarden, Proton — все, для кого доверие является продуктом.

## 4. Три линии защиты от случайной утечки секрета

### Линия 1 — `.gitignore`
Файлы с секретами не попадают в коммит по невнимательности. Уже настроено.

### Линия 2 — проверка перед коммитом (на вашем компьютере)
При каждом `git commit` запускается [`scripts/check-staged-secrets.mjs`](../scripts/check-staged-secrets.mjs):
он смотрит, что именно вы собираетесь отправить, и **не даёт закоммитить**
файл-ключ или строку, похожую на секрет. Ошибка ловится до того, как что-то
попало в историю.

Установка (один раз):

```bash
npm run hooks:install
```

> Почему свой скрипт, а не Gitleaks: Gitleaks — отдельная программа на Go,
> её нужно устанавливать вручную, и на Windows это лишний барьер.
> Наш скрипт работает сразу и не добавляет зависимостей. Gitleaks при этом
> остаётся в CI как **независимая** вторая проверка — две разные реализации
> ошибаются по-разному, и это хорошо.
>
> **Живой пример, почему узкие правила важнее широких.** Первая версия скрипта
> считала безопасной любую строку со словом `example`. Проверка на тестовом
> ключе `AKIAIOSFODNN7EXAMPLE` показала: ключ AWS проходил насквозь.
> Исключение сузили до `example.com`. Широкое исключение в проверке
> безопасности хуже, чем её отсутствие: оно создаёт ложное спокойствие.

### Линия 3 — проверка в CI (на стороне GitHub)
Даже если первые две линии обошли — CI просканирует **всю историю** репозитория
и провалит сборку. Настроено в [`.github/workflows/ci-security.yml`](../.github/workflows/ci-security.yml).

Плюс включается **GitHub Secret Scanning** (бесплатен для публичных репозиториев):
GitHub сам распознаёт формат ключей Stripe, Google, AWS и **уведомляет провайдера**,
чтобы тот отозвал ключ.

## 5. Если секрет всё-таки попал в git

Важно понять главное: **удалить строку и сделать новый коммит — недостаточно.**
Старый коммит остаётся в истории, его видно через `git log`, а для публичного
репозитория — ещё и через кэш GitHub и через зеркала, которые делают боты
в первые минуты после публикации.

Порядок действий — именно в этом порядке:

```
1. ОТОЗВАТЬ КЛЮЧ. Немедленно, прежде чем что-либо чинить в git.
   Ключ, побывавший в публичном репозитории, считается скомпрометированным
   навсегда — независимо от того, успел ли кто-то его увидеть.

2. Выпустить новый ключ и положить в .env на сервере.

3. Почистить историю git (git filter-repo) — это уже гигиена, а не защита.

4. Записать инцидент в PROJECT_LOG.md → Журнал решений.
```

Боты сканируют новые публичные репозитории на GitHub **в течение секунд** после
публикации. Реальные случаи компрометации ключей AWS измеряются минутами.

## 6. Настройка репозитория на GitHub

Что включить в настройках после первой публикации:

| Настройка | Где | Зачем |
|---|---|---|
| **Secret scanning** + Push protection | Settings → Code security | GitHub блокирует push с ключом |
| **Dependabot alerts** + security updates | Settings → Code security | автоматические PR с обновлением уязвимых библиотек |
| **Branch protection** для `main` | Settings → Branches | нельзя влить код мимо проверок CI |
| Require status checks | там же | пока CI красный — merge заблокирован |
| **Private vulnerability reporting** | Settings → Code security | исследователь сообщит о дыре приватно, а не в публичном issue |
| **CodeQL** | Security → Code scanning | бесплатный анализ кода для публичных репозиториев |

Полезно также добавить файл `SECURITY.md` — он уже создан в корне: там написано,
куда сообщать об уязвимости.

## 7. Публичный репозиторий ≠ открытая лицензия

Тонкость, которую часто путают. По умолчанию **код без лицензии защищён авторским
правом полностью**: смотреть можно, копировать и использовать — нельзя.

Если цель — «покажите, что код честный», то лицензия не нужна вообще:
достаточно файла `LICENSE` с формулировкой «все права защищены, код открыт
для ознакомления и аудита». Именно так и сделано.

## 8. Практический порядок публикации

```bash
git add .
git status
```

⚠️ Перед первым push обязательно глазами просмотреть вывод `git status` и убедиться,
что там **нет** строки `.env`. Затем:

```bash
git commit -m "Начальная структура проекта"
```

Создать репозиторий на GitHub **как публичный**, и перед первым push прогнать
проверку на секреты:

```bash
npx gitleaks detect --no-git -v
```

Только после чистого результата:

```bash
git push -u origin main
```

## 9. Чек-лист перед каждым push

```
□ git status не показывает .env, *.pem, *.key, terraform.tfvars
□ В коде нет настоящих email, телефонов, имён
□ В тестах используются вымышленные данные (example.com, +48 000 000 000)
□ Скриншоты не содержат реальных данных
□ npm run verify проходит
□ Gitleaks молчит
```
