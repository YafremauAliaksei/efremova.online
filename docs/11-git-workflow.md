## 1. Зачем ветки вообще

Знакомая картина:

```
📁 сайт_final
📁 сайт_final_2
📁 сайт_final_НОВАЯ_ИДЕЯ
📁 сайт_final_final_рабочая_НЕ_УДАЛЯТЬ
```

Здесь уже есть вся логика git — просто выраженная папками. Перевод:

| Папки с суффиксами | git |
|---|---|
| `сайт_final` — снимок состояния на момент времени | **коммит** |
| `сайт_final_НОВАЯ_ИДЕЯ` — копия, где пробуем не ломая рабочую | **ветка** |
| «вот эта точно работает, её не трогаем» | **`main`** |
| «идея получилась, переношу в рабочую» | **merge** (слияние) |

Разница только в том, что git делает это без копирования гигабайтов, помнит,
**от какого именно снимка** отпочковалась копия, и умеет свести две копии обратно,
даже если в обеих что-то поменялось.

**Главное, что нужно усвоить про `main`.**
`main` — это **не** «последняя версия» и **не** «самое свежее».
`main` — это **«версия, которая точно работает»**.

Из этого следует всё остальное. Недоделанное, непроверенное, «сейчас быстро гляну» —
живёт в ветках. В `main` попадает только то, что прошло проверки. Поэтому в `main`
и не пушат напрямую: прямой push означает «я записал в раздел „точно работает“
то, что никто не проверял».

В этом проекте у правила есть цена в деньгах и в законе: репозиторий публичный,
а код обрабатывает данные о здоровье. Сломанный `main` здесь — не «неудобно»,
а «в открытом доступе лежит битая версия приложения с медицинскими данными».

## 2. Словарь (три минуты, дальше не понадобится)

| Термин | Обычными словами |
|---|---|
| **Репозиторий** | Папка проекта + вся её история изменений |
| **Коммит** | Сохранённый снимок + записка «что и зачем я поменял» |
| **Ветка** | Цепочка коммитов с именем. Ответвление от общей линии |
| **`main`** | Главная ветка. «Версия, которая точно работает» |
| **`origin`** | Имя копии репозитория на GitHub. Буквально «источник» |
| **push** | Отправить свои коммиты на GitHub |
| **pull** | Забрать с GitHub то, чего нет у меня |
| **Pull Request (PR)** | Заявка: «предлагаю влить мою ветку в `main`». Место, где проходят проверки и ревью |
| **Merge** | Влить одну ветку в другую |
| **Конфликт** | Две ветки поменяли одни и те же строки, git не решает за вас, чей вариант верный |
| **CI** | Робот, который на каждый push прогоняет все проверки (у нас — 8 ворот) |

## 3. Цикл одной задачи — по командам

Это основной раздел. Команды идут ровно в том порядке, в котором их набирают.

### Шаг 1. Начать со свежего `main`

```bash
git checkout main
git pull origin main
```

`git checkout main` — переключиться на ветку `main`. Файлы в папке проекта
физически меняются на то, что записано в `main`.

`git pull origin main` — забрать с GitHub всё, чего нет локально.
Зачем, если работаете один? Потому что вы не один: **Dependabot** тоже делает
коммиты, а вы иногда правите файлы прямо в веб-интерфейсе GitHub. Коммит
`9c5b27b Update CODEOWNERS` в этой истории сделан именно так — из браузера.
Начать работу от устаревшего `main` — гарантированный конфликт через два часа.

### Шаг 2. Создать ветку под задачу

```bash
git checkout -b feat/admin-services
```

Флаг **`-b`** = _branch_, «создай ветку и сразу переключись на неё».
Без `-b` команда означала бы «переключись на существующую».

Ветка создаётся **от того места, где вы сейчас стоите**. Поэтому шаг 1
обязателен и идёт первым: ответвляемся от свежего `main`, а не от вчерашнего.

> Есть более новая пара команд — `git switch` (переключиться) и `git switch -c`
> (создать и переключиться). Делают то же самое, названы понятнее.
> Здесь используется `checkout`, потому что в 90 % чужих инструкций, ответов
> и статей вы встретите именно его. Знать надо оба, набирать — любой.

### Шаг 3. Работа. Смотреть на изменения часто

```bash
git status     # какие файлы затронуты
git diff       # что именно изменилось, построчно
```

`git status` — «что у меня сейчас на столе»: изменённые файлы, новые файлы,
что уже добавлено к будущему коммиту.

`git diff` — построчная разница. **Красное** — было, **зелёное** — стало.

Набирайте их часто, это бесплатно и ничего не меняет. Привычка смотреть
в `git diff` — то, что отличает человека, который знает, что он коммитит,
от человека, который коммитит `git add .` и надеется.

### Шаг 4. После каждой заметной правки — проверка

```bash
npm run verify
```

Типы + линтер + форматирование + тесты, около 40 секунд.
Смысл в том, чтобы ловить ошибку через минуту после того, как её написали,
а не через три часа среди десяти других изменений.

### Шаг 5. Коммит — маленькими законченными порциями

```bash
git add src/app/admin/services/page.tsx src/lib/admin/services.ts
git commit
```

`git add <файлы>` — выбрать, что войдёт в коммит. Именно **выбрать**:
у git есть промежуточная «корзина» (индекс), и это не лишняя сложность,
а возможность разложить работу по смыслу. Наработали на три темы — соберите
три коммита, а не один.

`git add .` («добавить всё») существует, но приучаться к нему не стоит:
однажды так в репозиторий уезжает временный файл, дамп базы или `.env`.
В этом проекте последнее поймает хук `pre-commit` — но полагаться на страховку
вместо привычки неправильно.

`git commit` **без `-m`** открывает редактор для полноценного сообщения.
Почему без `-m` — в разделе 5.

**Насколько маленькими?** Ориентир: коммит должно быть возможно описать одной
строкой без слова «и». Появилось «и» — это два коммита.

### Шаг 6. Перед push — полный прогон

```bash
npm run ci
```

Все 10 ворот, как на GitHub, 5–10 минут, нужен запущенный Docker.
Правило проекта, записанное кровью трёх красных прогонов подряд
([`10-how-we-work.md`](10-how-we-work.md)): **красный локально — не пушим.**

### Шаг 7. Отправить ветку на GitHub

```bash
git push -u origin feat/admin-services
```

Флаг **`-u`** = _set upstream_, «запомни, что моя локальная ветка
`feat/admin-services` соответствует одноимённой ветке на `origin`».
Нужен **только в первый push этой ветки**. Дальше достаточно просто `git push` —
git уже знает, куда.

> ⚠️ **Push делает только владелец, руками.** У ИИ-агента команда `git push`
> запрещена на уровне настроек (`.claude/settings.json`), и это не формальность:
> код уходит в публичный интернет только по осознанному решению человека.
> Подробнее — [`09-ai-agent-safety.md`](09-ai-agent-safety.md).

### Шаг 8. Открыть Pull Request

После push GitHub сам покажет в репозитории жёлтую полосу
«`feat/admin-services` had recent pushes» и кнопку **Compare & pull request**.

Или из командной строки:

```bash
gh pr create --fill
```

`--fill` подставит заголовок и описание из ваших сообщений коммитов —
ещё одна причина писать их по-человечески.

### Шаг 9. Дождаться зелёного CI и прочитать свой диф

На странице PR внизу — список проверок. Ждём, пока все станут зелёными.
**Красный CI не мержится никогда**, даже «потом починю» (см. раздел 7, привычка 7).

Пока идут проверки — вкладка **Files changed**, и вы читаете собственные изменения
как чужие. Это называется **self-review**. Удивительно, сколько в этот момент
находится: забытый `console.log`, закомментированный кусок, опечатка в комментарии,
случайно затронутый посторонний файл.

### Шаг 10. Merge и уборка

Кнопка **Merge pull request** на GitHub. Затем:

```bash
git checkout main
git pull origin main
git branch -d feat/admin-services
```

Флаг **`-d`** = _delete_. Важное свойство: `-d` **откажется** удалять ветку,
изменения из которой ещё никуда не влиты. Это защита — git проверяет, что работа
не потеряется. Если уверены, что ветка не нужна (эксперимент не удался),
есть `-D` — «удаляй, я знаю, что делаю».

> **Мелочь, которую в компаниях не объясняют.** Если мержить кнопкой
> **Squash and merge** (все коммиты ветки схлопываются в один), `git branch -d`
> скажет «ветка не слита» — потому что формально её коммитов в `main` нет,
> там лежит один новый, объединённый. Это нормально, и в этом случае `-D` уместен.

На GitHub после мержа появляется кнопка **Delete branch** — нажимайте,
она убирает ветку на сервере. Локальная и серверная ветки удаляются отдельно.

## 4. Как называть ветки

Формат: **`тип/краткое-описание-английскими-буквами-через-дефис`**

| Префикс | Когда | Пример |
|---|---|---|
| `feat/` | новая функция | `feat/admin-services` |
| `fix/` | починка поломки | `fix/cabinet-no-store-header` |
| `docs/` | только документация | `docs/git-workflow` |
| `chore/` | рутина: обновления, конфиги, зависимости | `chore/deps-major-upgrade` |
| `refactor/` | переписал внутри, снаружи поведение то же | `refactor/auth-providers` |

Правила: латиница, нижний регистр, слова через дефис, без пробелов и кириллицы
(они ломаются в URL и в чужих инструментах). Имя короткое, но по нему должно быть
понятно, о чём ветка, без открывания.

Ещё два префикса, которые встретятся в чужих проектах: `test/` (только тесты)
и `perf/` (ускорение без изменения поведения).

## 5. Сообщения коммитов

### Формат

```
Короткая строка до ~70 знаков

Пустая строка обязательна — по ней git отличает заголовок от тела.

Дальше подробности: ЗАЧЕМ это сделано, какую задачу решает,
что рассматривали как альтернативу и почему не выбрали.
Строки переносить примерно на 72 знаках.

Проверено: npm run ci — 10/10 зелёные.
```

**Почему ~70 знаков в первой строке.** Это не эстетика. `git log --oneline`,
список коммитов на GitHub, `git shortlog`, всплывающие подсказки при наведении —
везде показывается только первая строка, и всё длиннее обрезается многоточием.
Обрезанный заголовок = коммит, о котором надо гадать.

**Почему «зачем», а не «что».** «Что» уже записано в самом дифе, построчно
и точнее любого текста. Чего в дифе нет — это причины. Через полгода
(а в этом проекте — через день) вопрос будет ровно один: _почему так сделано?_

Плохо: `Поправил Dockerfile`
Хорошо: `Hadolint: одинаковый порог локально и на GitHub` + тело с объяснением,
почему в Alpine не фиксируют версии пакетов.

### Честный разбор ваших восьми коммитов

Вы просили прямо — говорю прямо.

**Что уже лучше, чем у большинства:**

Тела сообщений — сильная сторона, без скидок. Там есть причина, альтернатива,
строчка «Проверено: …» и записанный урок. В `9a753fb` объяснено не только
«что чинили», но и почему фиксировать версии пакетов в Alpine — вредный совет.
Такое в корпоративных репозиториях встречается редко. Формат соблюдён: заголовок,
пустая строка, тело.

**Что надо поправить — три вещи:**

**1. Длина первой строки.** Замерено:

| Коммит | Знаков в заголовке | Норма |
|---|---:|---|
| `9a753fb` | 140 | ~70 |
| `6ac815a` | 127 | ~70 |
| `f38d83d` | 125 | ~70 |
| `ca08440` | 123 | ~70 |
| `f0df243` | 104 | ~70 |
| `2dcc3aa` | 91 | ~70 |
| `77786ee` | 72 | ✅ |
| `9c5b27b` | 17 | ✅ |

Шесть из восьми — вдвое длиннее нормы. Лечится тем, что лишнее уезжает в тело.

**2. Слово «и» в заголовке — признак, что коммитов должно быть несколько.**

> `Зелёный CI, локальный прогон всех ворот, оптимизация образа и админка`

Это четыре независимые темы в одном коммите. Если завтра выяснится, что оптимизация
образа сломала сборку, откатить её отдельно нельзя — она приклеена к админке
и к локальному прогону CI. Размер подтверждает диагноз:

| Коммит | Объём |
|---|---|
| `6ac815a` | 60 файлов, +8275 строк |
| `ca08440` | 20 файлов, +1982 / −253 |
| `2dcc3aa` | 18 файлов, +946 / −60 |
| `f38d83d` | 14 файлов, +942 / −27 |

Ориентир для PR — до ~400 изменённых строк (раздел 7, привычка 3).
`6ac815a` при этом — законное исключение: это первый коммит проекта,
его не делят никогда и нигде.

**3. `Update CODEOWNERS` — единственный по-настоящему плохой коммит.**
Это подпись, которую GitHub подставляет сам, когда правишь файл в браузере.
Она сообщает ровно то, что и так видно из дифа, и ничего — о причине.
А правка была содержательная: в файл, который управляет всеми остальными защитами.
Через полгода на вопрос «почему здесь такой список владельцев» ответа не будет.

Вывод: **писать вы умеете, дробить — пока нет.** Первое — редкий навык,
второе — дисциплина, которая нарабатывается за неделю.

### Про префиксы `feat:` и `fix:` в коммитах

Вы их увидите в чужих проектах (это соглашение Conventional Commits), и Dependabot
в этом репозитории уже так пишет: `ci: Bump the all-actions group…`,
`deps: Bump @lhci/cli…`. Заводить это для себя не обязательно: префиксы нужны
прежде всего роботам, которые автоматически считают номер версии по истории
коммитов. Мы номера версий не выпускаем. Ветки у нас именуются по типу —
этого достаточно.

## 6. Pull Request — и зачем он, когда работаешь один

Это то место, где интуиция подводит чаще всего: «ревьюить меня некому, значит,
PR — пустая бюрократия». Не так. У PR четыре функции, и только одна из них — ревью.

**1. PR — это то, ГДЕ запускаются проверки.**
В нашем `ci-security.yml` два гейта объявлены так:

```yaml
if: github.event_name == 'pull_request'
```

**🎯 DAST (OWASP ZAP)** и **🚀 Lighthouse** запускаются только на pull request.
При прямом push в `main` они помечаются `skipped` и не выполняются вовсе.
Внутри DAST живёт `scripts/check-security-headers.mjs` — та самая блокирующая
проверка, которая однажды поймала отсутствие `no-store` и `noindex` на редиректе
закрытой зоны (требование №5 из `CLAUDE.md`). Работая через push, вы не просто
пропускаете ревью — вы **отключаете половину охраны** и не видите этого,
потому что пропущенный шаг выглядит серым, а не красным.

> 📌 У этой же проверки есть вторая поучительная история, из 2026-09-14.
> Она смотрела на `/cabinet`; кабинет вырезали, адрес исчез, Next.js стал
> отдавать 404 — а 404 по умолчанию несёт `no-store`. Проверка продолжила
> проходить, **ничего не проверяя**. Отсюда правило: проверка обязана падать,
> если проверяемого больше нет. Теперь статус 404 в ней считается провалом.

**2. PR — точка, где можно передумать.**
Коммит в `main` уже случился. PR можно закрыть без последствий: `main` не менялся.

**3. PR — это документ.**
Через полгода вопрос «почему мы перешли на Prisma 7» приведёт к PR, где лежит
описание, диф и вердикт всех проверок разом.

**4. PR — тренажёр.**
Через полгода в компании PR будет вашим основным способом отдавать работу.
Навык «нарезать изменения так, чтобы их можно было прочитать» нарабатывается
только практикой.

### Главное про PR, чего вы не знали: **PR живой**

Это не «отправил письмо и жди ответа». PR — это **постоянная ссылка на ветку**.

```
git push в ту же ветку
        ↓
PR обновился сам — новые коммиты появились в нём
        ↓
CI перезапустился с нуля на новом состоянии
        ↓
Новый PR открывать НЕ НУЖНО
```

Отсюда — правильная реакция на красный CI в PR:

```bash
# ...чиним то, на что ругается CI, прямо в той же ветке...
npm run verify
npm run ci
git add <файлы>
git commit
git push          # уже без -u: ветка привязана в шаге 7
```

Через несколько минут в том же PR проверки перезапустятся. Ничего закрывать,
пересоздавать и переоткрывать не надо. Красный CI — это рабочее состояние
незаконченного PR, а не провал.

## 7. Десять привычек, которые в компании не объясняют

Их считают само собой разумеющимися — и не рассказывают новичку, а молча отмечают,
что человек их не соблюдает.

**1. Никогда не коммитить в `main` напрямую. Ни разу, даже «на одну строчку».**
Исключений нет, потому что каждое исключение — это правка, которую никто не смотрел,
в ветке с названием «точно работает». «Одна строчка» — самая опасная формулировка
в разработке: именно её не проверяют.

**2. Один PR — одна тема.**
Обновление зависимостей и новая страница — два PR. Даже если делались в один вечер.
Иначе откатить одно без другого невозможно.

**3. PR маленький. Ориентир — до ~400 изменённых строк.**
Это не придирка, это про внимание человека: на большом дифе читающий (в том числе
вы сами через час) перестаёт видеть детали и начинает листать.

**4. Ветка живёт дни, а не недели.**
Чем дольше ветка в стороне от `main`, тем сильнее они расходятся и тем больнее
конфликты. Долгая ветка почти всегда означает, что задачу надо было разбить.

**5. `git pull` перед началом работы. Всегда.**
Дёшево, занимает секунду, экономит час на конфликтах.

**6. Никогда `git push --force` в ветку, которую видит кто-то ещё.**
`--force` переписывает историю на сервере. У всех, кто её уже скачал, репозиторий
становится несовместимым. В своей личной ветке до PR — допустимо
(и то лучше `--force-with-lease`: он откажется, если на сервере появилось
что-то, чего вы не видели). В `main` — никогда.

**7. Не мержить красный CI. Ни под каким «потом починю».**
«Потом» не наступает, а `main` перестаёт означать «точно работает».
Один раз влитый красный CI обесценивает все восемь ворот сразу.

**8. Не коммитить закомментированный код.**
«Закомментирую, вдруг понадобится» — это и есть мышление папок `_final_2`.
История git **и есть** архив: удалённый код достаётся `git log`/`git show`
в любой момент. Закомментированный код в файле только мешает читать.

**9. Читать свой диф перед PR.**
Вкладка Files changed, глазами, целиком.

**10. Удалять ветку после мержа.**
И локально (`git branch -d`), и на GitHub. Список из сорока мёртвых веток —
это место, где невозможно найти живую.

**Плюс одна, персональная для этого проекта:**
хук `pre-commit` проверяет staged-файлы на секреты. Обходить его флагом
`--no-verify` **нельзя** — так ключ и попадает в публичный репозиторий.
Если хук ругается, а вы уверены, что это ложное срабатывание — разбирайтесь
с правилом, а не с хуком.

## 8. Когда что-то пошло не так

Сначала общее — и это важнее конкретных команд.

> **В git почти ничего нельзя потерять безвозвратно.** Всё, что было хоть раз
> закоммичено, остаётся в репозитории, даже если ветка удалена, коммит «отменён»
> или история переписана. Есть команда `git reflog` — журнал всех перемещений
> `HEAD` за последние 90 дней:
>
> ```bash
> git reflog
> ```
>
> Вы увидите строки вида `a1b2c3d HEAD@{4}: commit: ...`. Вернуться в любую точку:
> `git checkout a1b2c3d`. По-настоящему теряются только изменения, которые
> **ни разу не коммитили**, — и то, если поверх них выполнить `git reset --hard`
> или `git checkout -- <файл>`.
>
> Практический вывод: бояться не нужно, нужно коммитить чаще. Коммит —
> это точка, в которую можно вернуться.

### Ситуация 1. «Закоммитил не то»

**Случай А — сообщение плохое, а сам коммит правильный.** Коммит ещё не отправлен:

```bash
git commit --amend
```

Откроется редактор, правите текст, сохраняете. Коммит заменяется новым.

**Случай Б — коммит не нужен, а работа нужна.**

```bash
git reset --soft HEAD~1
```

`HEAD~1` — «один коммит назад». `--soft` — «сдвинь указатель, а файлы и индекс
не трогай». Результат: коммита нет, все изменения на месте и уже добавлены
к следующему коммиту. Можно перебрать `git add` / `git commit` заново.

**Случай В — забыл добавить файл в только что сделанный коммит.**

```bash
git add забытый-файл.ts
git commit --amend --no-edit
```

`--no-edit` = «сообщение оставить прежним».

> ⚠️ **Всё это — только для коммитов, которые ещё не ушли на GitHub.**
> `--amend` и `reset` создают новую историю вместо старой. Если коммит уже
> запушен, замена потребует `--force` — см. привычку 6. Отправленное
> исправляют **новым коммитом**, а не переписыванием прошлого.

### Ситуация 2. «Конфликт при мерже»

**Что это.** Вы в своей ветке поменяли строку 42 в файле. Кто-то (или вы сами
из браузера, или Dependabot) поменял ту же строку 42 в `main`. При слиянии git
видит два разных варианта одной строки. Он **не угадывает**, чей верный —
это было бы опаснее, чем спросить.

Конфликт — **не поломка и не ваша ошибка**. Это нормальная часть работы.

**Как разруливать по шагам.**

1. Сначала подтянуть свежий `main` в свою ветку — конфликт лучше встретить
   у себя, а не в PR:

   ```bash
   git checkout main
   git pull origin main
   git checkout feat/моя-ветка
   git merge main
   ```

2. Если конфликт есть, git скажет `CONFLICT (content): Merge conflict in <файл>`
   и остановится. Посмотреть список:

   ```bash
   git status
   ```

   Нужные файлы — в разделе **Unmerged paths**.

3. Открыть каждый такой файл. Внутри — разметка:

   ```
   <<<<<<< HEAD
   вариант из вашей ветки
   =======
   вариант из main
   >>>>>>> main
   ```

   Ваша задача — **оставить правильный текст и стереть все три строки-маркера**
   (`<<<<<<<`, `=======`, `>>>>>>>`). Правильным может быть любой из вариантов
   или их комбинация — решаете вы, потому что только вы знаете смысл обеих правок.

4. Отметить, что файл разрешён, и завершить слияние:

   ```bash
   git add <файл>
   git commit        # git сам подставит текст «Merge branch 'main' into ...»
   npm run verify    # обязательно: после разбора конфликта код надо проверить
   ```

**Аварийный выход.** Если запутались — откатить слияние целиком, как будто
его не начинали:

```bash
git merge --abort
```

Возвращает ветку ровно в то состояние, что было до `git merge`. Безопасно.

### Ситуация 3. «Начал работу прямо в `main`, забыл создать ветку»

Возникнет обязательно. Лечится в две команды, ничего не теряется.

**Случай А — ещё не коммитили** (правки есть, `git status` показывает изменения):

```bash
git checkout -b feat/моя-ветка
```

И всё. Незакоммиченные изменения **переезжают вместе с вами** в новую ветку —
git их не трогает при переключении. `main` остаётся чистым.

**Случай Б — уже успели закоммитить в `main`, но не пушили:**

```bash
git branch feat/моя-ветка          # 1. поставить закладку на текущем месте
git reset --keep origin/main       # 2. вернуть main туда, где он на GitHub
git checkout feat/моя-ветка        # 3. перейти в свою ветку — коммиты здесь
```

Разбор:

1. `git branch <имя>` **без** `-b` и без переключения создаёт ветку, но оставляет
   вас на месте. Ваши коммиты теперь записаны под этим именем и потеряться не могут.
2. `git reset --keep origin/main` двигает локальный `main` обратно к состоянию
   GitHub. Флаг `--keep` — осознанный выбор: в отличие от `--hard`, он **откажется**
   выполняться, если при этом потерялись бы незакоммиченные правки.
   `--hard` в чужих инструкциях встречается чаще, но он стирает молча — начинайте
   с `--keep`.
3. Переключаемся в ветку и работаем дальше как обычно.

Проверить, что всё на месте:

```bash
git log --oneline -3        # ваши коммиты в ветке
git checkout main
git log --oneline -3        # main совпадает с GitHub
git checkout feat/моя-ветка
```

**Случай В — закоммитили в `main` и уже запушили.** Здесь чинить историю нельзя
(привычка 6: история `main` на сервере не переписывается). Живём дальше:
следующая задача — уже в ветке. Один такой коммит не трагедия; трагедия — привычка.

## 9. Шпаргалка на один экран

```bash
# ── начать задачу ──────────────────────────────────────────
git checkout main
git pull origin main
git checkout -b feat/имя-задачи

# ── в процессе ─────────────────────────────────────────────
git status                    # что на столе
git diff                      # что именно изменилось
npm run verify                # 40 сек: типы, линтер, формат, тесты
git add <файлы>
git commit                    # маленькими законченными порциями

# ── перед отправкой ────────────────────────────────────────
npm run ci                    # ОБЯЗАТЕЛЬНО: все 10 ворот, нужен Docker
git push -u origin feat/имя-задачи   # -u только в первый раз

# ── на GitHub ──────────────────────────────────────────────
# Compare & pull request  →  дождаться зелёного CI
# Files changed — прочитать свой диф глазами
# Merge pull request  →  Delete branch

# ── убрать за собой ────────────────────────────────────────
git checkout main
git pull origin main
git branch -d feat/имя-задачи

# ── если что-то пошло не так ───────────────────────────────
git reflog                    # журнал: куда я вообще ходил
git merge --abort             # отменить начатое слияние
git reset --soft HEAD~1       # отменить последний коммит, работу сохранить
git commit --amend            # переписать последний коммит (если не запушен)
```

## 10. Что из этого проверяет ИИ-агент

Чтобы документ не остался благим намерением, агент в каждой сессии обязан:

1. **Отказываться коммитить в `main`.** Если владелец просит внести правку,
   а текущая ветка — `main`, агент сначала называет команду создания ветки
   и ждёт, пока владелец её наберёт.
2. **Не набирать git-команды за владельца**, когда речь о процессе (ветки,
   коммиты, PR, мерж). Агент говорит, какую команду набрать и что она сделает.
   Цель — навык у человека, а не выполненная задача.
3. **Требовать `npm run ci` перед каждым push** и не предлагать push,
   пока прогон не зелёный.
4. **Останавливать разрастание PR.** Если в ветке набралось заметно больше
   ~400 изменённых строк или появилась вторая тема — сказать об этом вслух
   и предложить разделить.
5. **Никогда не выполнять `git push` самостоятельно** — запрещено
   в `.claude/settings.json`, см. [`09-ai-agent-safety.md`](09-ai-agent-safety.md).
