# 🛡️ 03 — Политика безопасности и ловушки для сканеров

Относится к основному домену — сайту-визитке. Личных данных клиентов на нём
нет (docs/13, раздел 10); требования к кабинету на поддомене будут описаны
вместе с ним.

## 2. Шифрование

| Где | Как |
|---|---|
| В пути | только TLS 1.3; HSTS `max-age=63072000; includeSubDomains; preload` |
| На диске | шифрованный том сервера; ночная резервная копия базы шифруется (`age`) — делается вместе с развёртыванием |
| Секреты | только в `.env` на сервере; в git, коде и логах — никогда |

## 3. Защита от конкретных атак

| Атака | Как закрыто |
|---|---|
| SQL-инъекция | Prisma параметризует всё; сырой SQL запрещён линтером |
| XSS | React экранирует; `dangerouslySetInnerHTML` запрещён правилом ESLint; CSP с nonce |
| CSRF | `SameSite=Lax` + проверка `Origin` / `Sec-Fetch-Site` на изменяющих запросах |
| SSRF | исходящие запросы сервера — только на заранее известные адреса |
| Кража сессии админа | cookie `__Host-`, httpOnly, Secure, 30 минут жизни |
| Clickjacking | `frame-ancestors 'none'` + `X-Frame-Options: DENY` |
| Прямой доступ к серверу мимо Cloudflare | 80/443 принимаются только с IP-диапазонов Cloudflare |
| Уязвимые зависимости | `npm audit` + Trivy + Dependabot в CI, lock-файл зафиксирован |

## 4. 🍯 Honeypot: ловушки для сканеров

### 4.1 Идея

Обычный посетитель никогда не откроет `/wp-admin/`, не заполнит невидимое поле
и не полезет в `/.env`. Кто это сделал — сканер уязвимостей. Ложных
срабатываний у ловушки нет: попасть в неё случайно нельзя.

### 4.2 Пять типов ловушек

```
ТИП 1 — ФАЛЬШИВЫЕ ПУТИ
  /wp-admin/, /wp-login.php, /.env, /.git/config, /phpmyadmin/,
  /admin.php, /config.json, /backup.sql, /.aws/credentials, /api/v1/debug
  → 404; первое попадание с адреса — с задержкой 2–5 с

ТИП 2 — НЕВИДИМОЕ ПОЛЕ ФОРМЫ
  <input name="website_url" tabindex="-1" aria-hidden="true">,
  спрятано CSS-ом, не display:none → заполнено = бот; форма «принята» и никуда не уходит

ТИП 3 — ПРИМАНКА В robots.txt
  Disallow: /internal-admin-v2/ → честный краулер послушается, сканер полезет туда

ТИП 4 — ФАЛЬШИВЫЙ API
  /api/internal/users?export=all → правдоподобные данные с email-«канарейками»:
  если такой адрес всплывёт, известны дата и IP источника

ТИП 5 — ВРЕМЕННАЯ ЛОВУШКА
  форма отправлена быстрее 1,5 с после загрузки → человек так не успевает
```

### 4.3 Что происходит после срабатывания

Запись идёт через ограничитель (`src/lib/security/throttle.ts`) и склеивается
в строку «адрес + тип + час» со счётчиком — подробно в docs/13, раздел 9.
Автоблокировка в Cloudflare отложена: поле `pushedToCloudflare` заполнится,
когда появится отдельная задача.

### 4.4 Защита от ложных срабатываний — понадобится вместе с автоблокировкой

Пока ловушки только записывают, ложное срабатывание ничего не стоит.
Когда появится автоблокировка, до неё обязательны:

| Риск | Страховка |
|---|---|
| Поисковый бот полезет в приманку | проверка reverse-DNS настоящих ботов Google/Bing |
| Мониторинг сам себя поймает | IP мониторинга в постоянном allowlist |
| Пентестер по договору | заголовок `X-Pentest-Token` отключает ловушки |

## 5. Заголовки безопасности (реализованы в коде)

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-{RANDOM}' 'strict-dynamic';
                         frame-ancestors 'none'; base-uri 'none'; form-action 'self';
                         object-src 'none'; upgrade-insecure-requests
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), interest-cohort=()
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: same-origin
```

Nonce генерируется заново на каждый запрос: вставленный в страницу `<script>`
без него браузер не выполнит. Поэтому запрещены inline-скрипты без nonce,
`eval()` и любые виджеты, требующие `unsafe-inline`. Сборка: `src/lib/security/headers.ts`.

## 8. Если взломали

```
1. ИЗОЛЯЦИЯ (0–15 мин)   Cloudflare → «Under Attack»; снимок диска до любых изменений
2. ОЦЕНКА (15–60 мин)    журнал событий, что затронуто, скомпрометированы ли ключи
3. УСТРАНЕНИЕ (1–6 ч)    ротация всех секретов, откат на чистый образ, закрытие дыры
4. УВЕДОМЛЕНИЕ (≤ 72 ч)  UODO, если есть риск для прав субъектов
5. РАЗБОР (неделя)       тест в CI, который поймал бы это раньше
```

## 9. Красные линии

1. **Секрет в git = инцидент.** Ротация ключа обязательна.
2. **Прод-база на личном компьютере — никогда.** Для разработки — только `prisma/seed.ts`.
3. **Ни одного чужого домена в браузере посетителя** — запрещено CSP, а не обещано.
4. **2FA для админского входа** — до выхода в прод.
5. **Бэкап без проверенного восстановления не считается бэкапом.**
6. **`console.log` с персональными данными блокирует слияние.**
7. **Новая зависимость требует обоснования** в описании PR.
8. **В `main` — только через PR, одобренный владельцем.** Агент PR не одобряет и не сливает.

## 10. Разработка с ИИ-агентом

Код пишет агент (Claude Code, в основном в облаке), одобряет и сливает владелец.
Защита строится так, чтобы ошибка агента или подброшенная ему инструкция
не дошла до `main` и не унесла секреты — даже если агент «согласится».

### 10.1 Рубежи

```
   Агент (облачный контейнер)
       │
   ┌───▼──────────────────────────────────────────────────────────┐
 1 │ СТОРОЖ .claude/hooks/guard-commands.mjs + deny в settings    │  ловит до сети
   │  терминал: push в main, force, --no-verify, токены из env,   │
   │  прямой API GitHub; коннектор: merge, auto-merge, approve,   │
   │  запись файлов через API, запуск workflow по ветке           │
   ├──────────────────────────────────────────────────────────────┤
 2 │ GITHUB PUSH PROTECTION: push с ключом отклоняет сам GitHub   │  до истории
   ├──────────────────────────────────────────────────────────────┤
 3 │ CI: восемь ворот, ни одного секрета в workflow               │  до слияния
   ├──────────────────────────────────────────────────────────────┤
 4 │ RULESET main: одобрение code owner на последний push,        │  граница
   │  обязательные проверки, без обходов                          │
   └──────────────────────────────────────────────────────────────┘
```

Сторож — сеть, а не стена: он в репозитории, и хитрую команду можно
сформулировать мимо разбора. Граница — рубеж 4: он на GitHub, агенту
недоступен и не зависит от того, что агент согласился сделать.

### 10.2 Почему у агента свой аккаунт на GitHub

Если агент действует от имени владельца, GitHub не отличает одного от другого:
всё, что разрешено владельцу, разрешено агенту, а обязательное одобрение
невозможно — автор PR не одобряет свой PR. Поэтому:

| | Владелец | Агент (машинный аккаунт) |
|---|---|---|
| Роль в репозитории | owner, единственный в `CODEOWNERS` | collaborator |
| Создаёт ветки и PR | да | да |
| Одобряет PR | да — это и есть подпись | нет: одобрение не от code owner не засчитывается |
| Меняет настройки, ruleset, секреты | да | нет прав |

Одобрение сбрасывается новым push: слить можно только тот код, который
владелец видел.

### 10.3 Облачное окружение

- Секретов в окружении облачной сессии нет: проекту для `verify` они не нужны.
- Токен GitHub в контейнере есть (его выдаёт облако для git и коннектора);
  сторож запрещает его читать, граница на случай обхода — рубеж 4.
- Сеть — ограниченный список (npm, GitHub), не полный доступ.
- Сессию готовит `.claude/hooks/session-start.mjs`: `npm ci --ignore-scripts`,
  клиент Prisma, `core.hooksPath` — чтобы проверка секретов перед коммитом
  работала и в облаке.

### 10.4 Что агент не делает никогда

Сливает, одобряет и автосливает PR; пишет в `main`; переписывает историю и
удаляет ветки на GitHub; меняет настройки, ruleset и секреты; запускает
workflow по своей ветке; читает токены из окружения. Правки CI, git-хуков и
правил агента — только по просьбе владельца и с его «да» при push.
