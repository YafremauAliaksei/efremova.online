## Часть 1. Кнопка, которая знает правду о себе

### 1.1 Чем плох обычный подход

Типовое решение — флажок в настройках: «Google-вход: вкл/выкл».
Проблема в том, что флажок отражает **намерение**, а не **реальность**.

```
Январь:  настроили Google-вход, флажок «вкл» ✅ — работает
Август:  в Google Cloud почистили проекты, ключ удалён
Август:  флажок по-прежнему «вкл» ❌
         → клиент жмёт кнопку → чужая страница ошибки Google
         → клиент решает, что сайт сломан, и уходит
```

Владелец узнаёт об этом от клиента. В худшем случае — не узнаёт вообще.

### 1.2 Как сделано у нас: две ступени

Реализация была в `src/lib/auth/providers.ts` — файл удалён, см. врезку в начале документа

```
┌─────────────────────────────────────────────────────────────┐
│ СТУПЕНЬ 1 — КОНФИГУРАЦИЯ         (мгновенно, без сети)      │
│ Заданы ли нужные переменные окружения?                      │
│   нет → NOT_CONFIGURED «метод не подключён»                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ да
┌───────────────────────────▼─────────────────────────────────┐
│ СТУПЕНЬ 2 — ЖИВАЯ ПРОБА          (запрос к провайдеру)      │
│ Принимает ли провайдер наши ключи ПРЯМО СЕЙЧАС?             │
│   да        → AVAILABLE        кнопка активна               │
│   отверг    → MISCONFIGURED    «недоступно»                 │
│   молчит    → PROVIDER_ERROR   «временно недоступно»        │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 Как именно проверяется каждый провайдер

Тонкий момент: нельзя же «попробовать войти» — для этого нужен живой пользователь.
Поэтому для каждого провайдера подобран безопасный приём.

| Провайдер | Приём | Как отличается «ключ жив» от «ключ мёртв» |
|---|---|---|
| **Google** | Запрос на обмен заведомо недействительного refresh-токена | `invalid_grant` = «токен плохой, но тебя я знаю» → ключ жив ✅<br>`invalid_client` = «я тебя не знаю» → ключ отозван ❌ |
| **Apple** | Подписываем клиентский JWT и шлём фиктивный код | Ошибка подписи локально → ключ битый ❌<br>`invalid_grant` → подпись принята ✅<br>`invalid_client` → Team ID / Key ID неверны ❌ |
| **Telegram** | `getMe` — запрос данных бота | `200 ok:true` → бот жив ✅<br>`401` → токен отозван в @BotFather ❌ |
| **WhatsApp** | Запрос собственного номера через Graph API | `200` → токен действует ✅<br>`401/403` → токен истёк ❌ |

Приём с Google особенно удобен: он не затрагивает ни одного пользователя,
не передаёт персональных данных и точно различает две причины отказа.

### 1.4 Принцип «сомневаешься — выключай» (fail-closed)

Если проба не удалась — таймаут, обрыв сети, непонятный ответ — кнопка **гаснет**.

Это сознательный выбор. Альтернатива («не знаем — оставим включённой») приводит
к тому, что клиент упирается в ошибку. Честное «временно недоступно, попробуйте
другой способ» лучше, чем кнопка, ведущая в тупик.

### 1.5 Как быстро кнопка вернётся после починки

Кэш проб с разным сроком жизни:

| Состояние | Проверяем раз в | Почему так |
|---|---|---|
| Работает | 10 минут | Не дёргаем провайдера зря, не тормозим страницу |
| Сломано | **1 минуту** | Починили ключ — кнопка вернётся в течение минуты, без перезапуска сайта |

Значения настраиваются: `AUTH_PROBE_TTL_OK_MS` и `AUTH_PROBE_TTL_FAIL_MS`.

### 1.6 Что видит посетитель, а что — только вы

| | Посетитель (прод) | Вы (режим разработки) |
|---|---|---|
| Кнопка работает | активна | активна |
| Не настроено | «не подключено» | `[dev] NOT_CONFIGURED: не заданы GOOGLE_CLIENT_ID` |
| Ключ отозван | «недоступно, мы уже знаем» | `[dev] MISCONFIGURED: Google отверг учётные данные` |
| Провайдер молчит | «временно недоступно» | `[dev] PROVIDER_ERROR: не ответил вовремя` |

Техническая причина в проде скрыта намеренно: имена внутренних переменных —
это подсказка атакующему об устройстве системы. А вот **имена** переменных
(не значения!) полезно показывать в разработке — сразу видно, чего не хватает.

### 1.7 Мониторинг

Эндпоинт `/api/auth/status` (тоже удалён) отдавал состояние
всех методов машиночитаемо. Если недоступны **все** способы входа — отвечает `503`.

Это важно: сайт при этом внешне работает, главная открывается, и обычный
мониторинг «сайт жив?» ничего не заметит. А войти в кабинет уже нельзя.
В Sprint 6 на этот эндпоинт вешается алерт в Telegram.

### 1.8 Как добавить новый способ входа

Один объект в массиве `METHODS` — и всё остальное (страница входа, эндпоинт
статуса, мониторинг) подхватит его само:

```ts
{
  id: 'vk',
  label: 'VK ID',
  hint: 'Вход через аккаунт VK',
  thirdPartyDataFlow: 'VK увидит ваш IP-адрес и факт входа.',
  requiredEnv: ['VK_CLIENT_ID', 'VK_CLIENT_SECRET'],
  probe: probeVk,
}
```

## Часть 2. Утекает ли IP — сравнение со шрифтами

### 2.1 Что было со шрифтами Google

Вопрос владельца точный и по делу. Ситуация со шрифтами такая:

```
Посетитель открывает страницу
        │
        │ в HTML стоит ссылка на fonts.googleapis.com
        ▼
Браузер САМ, без ведома человека, идёт к Google
        │
        ▼
Google получает: IP-адрес, User-Agent, какую страницу смотрят (Referer)
```

Человек **ничего не выбирал** — он просто открыл сайт психолога.
Немецкий суд (Мюнхен, 2022) признал это нарушением GDPR: передача IP третьей
стороне без правового основания. Именно поэтому у нас шрифты локальные —
это правило зафиксировано жёстко (docs/04, правило №3).

### 2.2 Чем принципиально отличается вход через Google

```
Посетитель открывает /login
        │
        │ ❌ НИКАКИХ обращений к Google из браузера
        │ ✅ доступность проверил НАШ СЕРВЕР со своего IP
        ▼
Человек читает, что увидит каждый сервис
        │
        │ ✅ и только если САМ нажимает кнопку
        ▼
Браузер идёт к Google → Google видит IP
```

Три отличия, и каждое существенно:

| | Шрифты | Вход через Google |
|---|---|---|
| Кто инициирует | браузер автоматически | **человек нажатием** |
| Знает ли человек | нет | **да, написано прямо на странице** |
| Можно ли избежать | да — раздавать со своего домена | нет — такова природа входа через чужой аккаунт |
| Есть ли альтернатива | не нужна | **да — вход по коду в Telegram** |

То есть здесь передача IP — это **осознанное действие пользователя**,
а не скрытая утечка. По GDPR у этого есть законное основание: согласие,
выраженное явным действием, и необходимость для исполнения услуги (ст. 6).

### 2.3 Что реализовано, чтобы не было «утечки до клика»

Перечисляю конкретно, потому что именно здесь легко всё испортить незаметно:

1. **Проба доступности — только на сервере.** Файл `providers.ts` начинается
   с `import 'server-only'`: если кто-то однажды по ошибке подключит его
   в браузерный компонент, **сборка упадёт**. Это не договорённость, а механизм.
2. **Нет `<link rel="preconnect">` к accounts.google.com.** Такой тег ускоряет
   вход на 100–200 мс, но заставляет браузер соединиться с Google заранее —
   то есть ровно та же утечка, что и со шрифтами. Отказались сознательно.
3. **Нет SDK провайдеров на странице.** Ни `gsi/client` от Google, ни Apple JS —
   это сторонние скрипты, которые к тому же ломают CSP с nonce (docs/03, п.5).
   Вход реализован обычным редиректом.
4. **Иконки провайдеров — локальные SVG**, не с их CDN.
5. **Геолокация — по заголовку Cloudflare**, а не через сторонний geo-IP сервис.
   Иначе IP каждого посетителя уходил бы ещё и туда.

### 2.4 Что написано в политике конфиденциальности

GDPR требует не только не течь, но и **предупреждать**. Поэтому блок
«Что видит внешний сервис при входе» стоит прямо на странице входа,
до нажатия кнопки, а не спрятан в подвале документа на 12 страниц.

Для каждого метода указано отдельно, и текст живёт рядом с самим методом
в коде (`thirdPartyDataFlow`) — чтобы не забыть обновить при добавлении нового.

### 2.5 Самый приватный способ входа

Если приватность важнее удобства — **Telegram OTP**:

| | Google / Apple | Telegram OTP |
|---|---|---|
| Кто узнаёт о факте входа | Google / Apple | Telegram (только факт сообщения от бота) |
| Получает ли IP сайта третья сторона | да | **нет** |
| Нужен ли аккаунт у корпорации | да | нужен Telegram |
| Удобство | одно нажатие | ввести 6 цифр |

Поэтому Telegram стоит в списке как равноправный вариант, а не «запасной».
Для аудитории психолога — часто это ещё и самый привычный канал.
