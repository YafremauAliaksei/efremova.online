# 🔄 10 — Как устроена работа: цикл, проверки и обратная связь

> Документ появился после честного вопроса владельца:
> «ты работаешь полчаса, говоришь „делай push“, потом оказывается, что проверки
> не проходят — а я не понимаю, что не так и чему тут учиться».
>
> Вопрос справедливый, и проблема была системной. Здесь — что именно было
> не так, как теперь, и как читать происходящее.

---

## 1. Что было сломано в самом процессе

Три захода подряд выглядели одинаково:

```
работа → «готово, push» → GitHub краснеет → разбор → снова push
```

Причина не в невнимательности. Часть проверок запускалась **только на GitHub**:

| Проверка | Раньше можно было запустить локально? |
|---|---|
| Типы, линтер, формат, тесты | ✅ да — и они не падали ни разу |
| Gitleaks (секреты) | ❌ нет |
| Hadolint (качество Dockerfile) | ❌ нет |
| Trivy (уязвимости в образе) | ❌ нет |
| Checkov (ошибки в Terraform) | ❌ нет |

То есть пять ворот из восьми проверялись вслепую. Узнать их вердикт можно было
только одним способом — отправить код и подождать. Отсюда и цикл.

**Это и есть «косяк со старта»:** конвейер проверок был спроектирован раньше,
чем способ его локально прогонять.

---

## 2. Что теперь: те же ворота на вашей машине

```bash
npm run ci
```

Запускает **все** проверки GitHub локально, в тех же контейнерах и тех же версиях.
Вывод устроен так, чтобы по нему можно было учиться:

```
[1/10] Типы TypeScript... OK
[2/10] Линтер... OK
...
[9/10] Уязвимости в образе (может занять несколько минут)... ОШИБКА

─── Уязвимости в образе ───
Ворота на GitHub: 🐳 Docker и Terraform
Что проверяет:    Trivy проверяет системные библиотеки и содержимое образа
Команда:          docker run --rm ... aquasec/trivy:latest image ...

Вывод (последние строки):
  │ tar (package.json) │ CVE-2026-59873 │ CRITICAL │ ...
```

Видно: какие ворота, что они значат, какой командой повторить, что именно нашлось.

Быстрая версия без Docker — типы, линтер, формат, тесты, аудит:

```bash
npm run ci:quick
```

**Правило:** зелёный `npm run ci` → зелёный GitHub. Если расходится — расхождение
само по себе баг, и чинить надо его, а не «перезапустить и посмотреть».

---

## 3. Три уровня проверок — и когда какой нужен

| Команда | Время | Когда запускать |
|---|---|---|
| `npm run verify` | ~30 сек | во время работы, после каждой заметной правки |
| `npm run ci:quick` | ~40 сек | перед коммитом |
| `npm run ci` | 5–10 мин | **перед push** |

Git-хук уже делает часть работы автоматически: перед каждым коммитом проверяет
секреты и форматирование.

## 4. Как читать, что происходит

Чтобы работа не выглядела как «полчаса тишины, потом готово», договорённость такая:

**В начале задачи** — план из нескольких пунктов: что будет сделано и в каком порядке.

**По ходу** — заметные развилки называются вслух: «нашлась причина падения — тег
действия без префикса v», а не просто «исправил».

**В конце** — три вещи:

1. **Что проверено и как.** Не «работает», а «команда X вернула Y».
2. **Что найдено попутно.** Баги, найденные при проверке, важнее сделанной работы:
   они показывают, где система слаба.
3. **Что осталось и что нужно от вас.**

Если какой-то шаг непонятен — вопрос «зачем это» уместен всегда. Половина решений
в этом проекте — компромиссы, и у каждого есть цена, которую полезно знать.

---

## 5. Почему проверок так много — и почему это не паранойя

Проект обрабатывает данные о здоровье и платежи. Разница между обычным сайтом
и этим — в цене ошибки: обычный сайт при утечке теряет репутацию, здесь речь
о врачебной тайне и штрафах GDPR.

Но у большого числа ворот есть своя цена: если они краснеют по пустякам, на них
перестают смотреть. Поэтому в проекте действует правило:

> **Каждое падение CI должно означать настоящую проблему.**
> Если проверка упала на ерунде — чинится проверка, а не отключается гейт.

Примеры уже принятых решений в эту сторону:

- `npm audit` блокирует только **production**-зависимости: уязвимости в Lighthouse CI
  на сервер не попадают, и падать на них — приучать себя не замечать красное;
- принятые риски живут в `scripts/check-audit.mjs` **со сроком годности** —
  когда срок выйдет, проверка упадёт сама;
- Trivy не ругается на npm внутри образа, потому что npm из образа удалён —
  не подавили предупреждение, а убрали причину.

## 6. Что делать, когда CI всё-таки красный

```
1. npm run ci          — воспроизвести локально
2. Прочитать блок про упавшую проверку: там есть и причина, и команда
3. Починить причину, а не симптом
4. npm run ci          — убедиться
5. git push
```

Если локально зелено, а на GitHub красно — это отдельный интересный случай:
значит, окружения разошлись. Такое уже случалось (тег действия без префикса `v`
проверялся только на стороне GitHub) и каждый раз даёт повод улучшить
локальный прогон.
